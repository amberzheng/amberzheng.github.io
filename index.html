eSIM: tap an offer, get a live line

China Unicom · product localisation & ecosystem delivery · first-of-its-kind nationwide Apple iOS eSIM rollout
Buying a line meant a store visit. eSIM moves the purchase onto the device — where Apple and Huawei own the final step and we own the refund.
My role: product owner of the journey. Turn business requirements into system flows, get four parties to one launch gate.
Specified the order state machine with a resume path at each hand-off; made provisioning idempotent so a retry can never mint a second SIM; mapped every failure code to a care script before launch.
Nationwide online eSIM live, including the first iOS rollout of its kind in the market.
shape · request sequence
stack · what each layer answers
H5 / app order page“Can this handset even do eSIM?”iPhone 14 · iOS 16.2 · unlocked → plan list; unsupported model → entry hidden
BSS order API“How do I hold a number and the money?”order 88213 reserves MSISDN + ICCID for 30 min
Real-name KYC“Is this really who they say?”ID + liveness · 3 retries · order stays PAID, not FAILED
Entitlement server“Is this device allowed to activate this line?”iOS asks the carrier before it shows “Activate eSIM”
SM-DP+ (GSMA ES2+)“Where does the profile itself come from?”prepareProfile(key=88213) → activation code, once only
LPA on device“How does the profile get onto the phone?”handset downloads from the SM-DP+ address, installs, notifies back
Care console“What do we tell someone whose download failed?”E-DL-408 → “resend code” button, no refund needed
mechanism · idempotent provisioning

// one transition table — product, eng and care read the same thing
const NEXT = {
  CREATED:       { pay:'PAID',        expire:'CANCELLED' },
  PAID:          { kyc_ok:'VERIFIED',  kyc_fail:'REFUND' },
  VERIFIED:      { issued:'READY',     issue_err:'RETRY' },
  READY:         { installed:'ACTIVE', timeout:'RESEND_CODE' },
};

// same key ⇒ same profile: a retry can never mint a second SIM
await smdp.prepareProfile({ idempotencyKey: order.id,
                            eid: device.eid, iccid: held.iccid });

on('issue_err', e => emit('esim_fail', { code: e.code, step: 'provision' }));

mechanism · a vote that survives scrutiny
ballot.sql
-- roll frozen the second the chair opens the motion
INSERT INTO ballot_roll (motion_id, member_id, token)
SELECT :motion, m.id, gen_random_uuid()
FROM members m
WHERE m.status = 'APPROVED' AND m.approved_at < :opened_at;

-- one member, one vote — enforced by the database, not the UI
CREATE UNIQUE INDEX ON votes (motion_id, member_id);

-- token burns on use; a replay returns the same receipt
UPDATE ballot_roll SET used_at = now()
WHERE token = :token AND used_at IS NULL RETURNING member_id;
-- 0 rows ⇒ already voted, shown as a receipt — never as an error

The rush: half-price stock, one open moment

National digital campaigns · “50% top-up” serving 6M+ users in one day · sign-in channel at 4M+ cumulative users
A limited pool of half-price top-ups opens at a fixed second. Scarcity concentrates demand — and lands a year of traffic in ninety seconds.
My role: campaign mechanics plus cross-team launch readiness — marketing timing, capacity planning, care staffing, all against one countdown.
Set a p99 budget of one second for a definite answer; moved the claim into a single atomic Redis hop so stock can’t oversell; kept the database out of the spike behind a queue; made “sold out” a designed screen with the next drop time and a reminder toggle.
6M+ users served in a day with stability held; the linked daily sign-in channel reached 4M+ cumulative users.

stack · what each layer answers
CDN static lobby“How do millions read a countdown for free?”prebuilt HTML at the edge · backend untouched until T−0
Server-synced clock“How does everyone see the same T−0?”client offset corrected against server time, not device time
Token-bucket gate“How do I admit only what the backend can take?”~400k rps arriving, 20k rps admitted, rest queued or told “next drop”
Redis + Lua“How do I claim stock without overselling?”check-user + decrement in one atomic script, no lock

mechanism · no oversell, no double claim
claim.lua — one atomic hop, three outcomes, three screens
-- KEYS[1] stock · KEYS[2] claimed-user set · ARGV[1] uid
if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then
  return -1                    -- already claimed → show their code
end
local left = tonumber(redis.call('GET', KEYS[1]))
if not left or left <= 0 then
  return 0                     -- sold out → next-drop + remind me
end
redis.call('DECR', KEYS[1]); redis.call('SADD', KEYS[2], ARGV[1])
return left - 1            -- claimed → order queued async

Behaviour tracking: find the stage that leaks

Data-driven optimisation · behaviour and campaign analysis turned into product, operational and iteration decisions
After a campaign there was a total and several theories. A total can’t say whether people never saw the offer, failed identity, or lost the race for stock.
My role: define the measurement — event contract, funnel stages, and the cuts the team argues with.
One event contract across web and webview, variant on every payload, failures logged as coded events; the pipeline below carries it from the browser to a board the ops team watches during the drop.
Drop-off located by stage and segment, turned into recommendations for product flows, operational strategy and the next iteration.
stack · what each layer answers
Matomo“What happened in the browser?”tap_claim fires with variant=B, province=Henan, device=Android 13
Nginx“How do I receive many HTTP requests efficiently?”the beacon endpoint absorbs the T−0 burst and just writes access logs
Filebeat“How do I cheaply ship continuously growing logs?”tails the log, remembers its offset, backs off instead of dropping lines
Logstash“How do I transform events?”parse JSON, drop bots, map error_code E-DL-408 → stage “profile download”
Kafka“How do I buffer and distribute huge event streams?”90-second burst absorbed; billing, BI and alerting each read at their own pace
Elasticsearch“How do I search and analyse all of it?”aggregate claim_result by variant × province, p95 of wait_ms
Kibana“How does a human explore and visualise it?”live funnel board during the drop; post-mortem cuts the morning after

Order migration with the exit kept open

User order system · legacy portal → new platform · plus rollout of a digital marketing learning platform
Live orders, real money, and downstream reports built on fields whose meaning had quietly drifted between teams.
My role: contribute the phasing and own the organisational half — who reads this data, what breaks for them, when they move.
Dual write with legacy as truth, shadow reads compared field by field, backfill reconciled nightly, canary widened only on a numeric gate, legacy kept warm after cutover.
Served from the new platform with no window where an order was unaccounted for; better efficiency and cross-team data collaboration.
shape · traffic to the new system
stack · what each layer answers
Field mapping contract“Do both systems mean the same by ‘status’?”legacy CLOSED = paid + delivered; new platform split it in two
Dual write“How does the new system get real data early?”every new order lands in both; legacy stays the system of record
Message bus mirror“How do we mirror without user-visible latency?”async publish, retried; checkout never waits for it
Shadow read + diff“Would the new system have answered the same?”both queried, legacy served, mismatches counted per field
Backfill + reconcile job“Do counts, totals and statuses match every night?”batch by month, then a daily automated reconciliation
Feature-flag canary“How do we widen traffic safely?”1% → 10% → 50%, province by province, on a numeric gate
Legacy kept warm“How do we go back?”still receiving writes after cutover, until consumers have moved

Learning channel for provincial teams

Digital training initiative · channel operations supported with data analysis · learn, test, certify, measure
Products designed centrally, executed in every province. Training was documents and occasional sessions, so gaps only surfaced when a launch went badly somewhere.
My role: design the channel — module format, test rules, retake policy, permissions — and analyse what the results meant.
Treated completion as a funnel, made a failed test return the learner to the missed lesson only, and used item analysis to tell a broken question apart from an unprepared team.
One training channel across provincial teams, with visible completion and score data replacing assumptions about readiness.
shape · module lifecycle
stack · what each layer answers
Module + item bank“What must a team know before this campaign?”one product change → one short module with items attached
Assignment + reminders“Who has to do it, by when?”the biggest drop sits here — scheduling, not content
Learner view“Can this be done on a phone between customers?”5-minute lessons, resumes exactly where they stopped
Test engine“How is a retake not the same paper twice?”items drawn randomly from the bank per attempt
Certification record“Who is cleared to run the campaign?”province checks the record before assigning campaign duties

Province dashboard“Where is the gap, and whose is it?”own teams vs national average; HQ sees what to republish
mechanism · blame the item, not the learner
item-analysis.sql
SELECT item_id,
       AVG(correct)               AS p_value,        -- too hard?
       CORR(correct, total_score) AS discrimination, -- or just bad?
       COUNT(*)                   AS attempts
FROM attempt_items JOIN attempts USING (attempt_id)
GROUP BY item_id
HAVING AVG(correct) < 0.4
   AND CORR(correct, total_score) < 0.2;
-- strong learners failing it too ⇒ rewrite the question
